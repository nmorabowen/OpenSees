| **WP-259 — thread-safe Ladruno concretes** ([[259_thread_safe_concretes]]; follows WP-258's pattern). Before: neither concrete answered `Material::ladrunoThreadSafeUpdate()` / `ladrunoThreadSafeForm()`, so `stdBrick`, `LadrunoQuad` and `ASDShellQ4` + `LayeredShell` holding one always ran serial. **Audit** (§2, written before any code change): both kernels are header-only and pure (constants and one `thread_local` call counter); every worker-path method touches only its own instance, the `thread_local` `ops_TheActiveElement` (crack-band `lch`) and read-only `ops_Dt`; neither material keeps a process-wide FP accumulator. **Fixes:** LadrunoConcrete3D's process-wide return-map warning budget becomes an atomic `fetch_add` claim (same 20 lines and suppression line serially, no overshoot threaded); every worker-path `opserr` (return-map failure, σ₂₂ / σ₃₃ condensation, Gc/lch range, `-verbose` commit summary, RC `-autoRegularization` loud failure, BeamFiber non-convergence, IMPL-EX error) is behind `LadrunoOutputGuard`; RC's BeamFiber interlock warn-once is `std::atomic<bool>`. **Opt-in:** LadrunoConcrete3D on ThreeDimensional / PlaneStrain / PlaneStress / PlateFiber and LadrunoRCConcrete on ThreeDimensional / PlaneStress / PlateFiber, every option; AxiSymmetric and BeamFiber views stay serial (no threaded host requests them). MPM mode F refuses both at admission (ADR 232 §6), so the opt-in does not reach it.
