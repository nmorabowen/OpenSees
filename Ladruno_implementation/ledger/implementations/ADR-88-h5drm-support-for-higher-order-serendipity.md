| **ADR-88 — H5DRM support for higher-order (serendipity) solid elements** ([[86_ladruno_h5drm_higher_order_elements_adr_pxp]], full design + implementation log in the CERN ATLAS DRM project, `notebooks/01_calibration_drm_soil/drm_load_pattern/`) — `H5DRMLoadPattern` previously required EVERY node of a DRM-boundary element to match a real ShakerMaker station directly; a quadratic element's mid-edge nodes never do (the grid is native to a linear/corner mesh), so `DRM_Elements` stayed empty and the DRM excitation silently applied zero force for any 2nd-order element (`BezierTet10`, `LadrunoBrick20`, `TenNodeTetrahedron`, `Twenty_Node_Brick`) — see `06_h5drm_higher_order_element_bug.md`. Fix: new pure interface `DRMHigherOrderNode` (`getDRMInterpolation(localNode, primaryLocalNodes, weights)` — false for a primary/corner node, true + a linear combination of the element's own primary nodes for a secondary/mid-edge node) that a solid `Element` subclass MAY additionally implement; `H5DRMLoadPattern::do_intitialization()` now resolves an unmatched node via `dynamic_cast<DRMHigherOrderNode*>` on its owning elements (all parents must already be directly-matched real stations — v1 does not chain interpolated-from-interpolated), and `resolveInterpolatedNodeMotions()` (called once per step from `ComputeDRMMotions`, after the existing `drm_direct_read`) fills `DRM_D`/`DRM_A` for those nodes as the same linear combination of the ALREADY-computed parent values — exact, not a second approximation, since spatial and temporal linear interpolation commute; zero changes to the dense/historically-buggy HDF5 read path itself. The boundary/interior classification (`DRM_Boundary_Flag`) of an interpolated node is derived geometrically (nearest real ShakerMaker station to the node's own true coordinates, no `distance_tolerance` requirement) rather than by voting between parents — empirically, parent disagreement is the COMMON case for a 1-element-thick transition layer (DRMBox's own two nested shells are exactly one element apart), not an edge case, so voting can never resolve the tie by construction. Implemented for `BezierTet10` (6 mid-edge nodes, reuses its own existing `edgeV[6][2]` table verbatim), `LadrunoBrick20` (12 mid-edge nodes, table read off `LadrunoHex20Shape.h`'s own documented k8-19 convention), and vanilla `TenNodeTetrahedron` (6 mid-edge nodes, table read off this class's own `shp[3][4..9]`, including its historical N8↔N9 index swap already marked `// *` in that file). Independent Python geometric oracle (T0, `t3_build_model.py::t0_geometric_oracle`, no shared code with the C++ tables) confirms every secondary node of the real apeGmsh-generated mesh is the true midpoint of some pair of its element's primary nodes: 1,066,464 checked / 0 failed (`BezierTet10`/`TenNodeTetrahedron` mesh), 414,720 checked / 0 failed (`LadrunoBrick20` mesh). Real SLURM run (Esmeralda, `OpenSeesMP`, 16 ranks, LOH1 `.h5drm` from ShakerMaker) confirmed `BezierTet10` goes from `Found 0 elements on DRM boundary` (the original bug) to `Found 880-2339 elements on DRM boundary` per rank with thousands of interpolated nodes resolved and no errors. Companion fixes shipped in the same effort (see `LEDGER_vanilla_files.md`/`LEDGER_quirks.md`): `FEM_ObjectBrokerAllClasses.cpp` missing `TenNodeTetrahedron`/`Twenty_Node_Brick` broker registration (parallel-only breakage), and `H5DRMLoadPattern::CalculateBoundaryForces`'s `MaxNodes=8` hardcoded buffer overflow for any >8-node element. Non-goals (explicit): `ASDAbsorbingBoundary3D` (hex8-fixed constructor, same pattern as the non-H5 DRM path's `GeometricBrickDecorator`) is NOT generalized to higher order — a T3 comparison model uses the plain Rayleigh-buffer boundary (`00_drm_free_field.ipynb`'s configuration) instead; `Twenty_Node_Brick` has no `apeGmsh` Python wrapper so is exercised only via `LadrunoBrick20 -formulation std`'s documented 1e-12 numerical equivalence, not directly. **B4 — primary-node nearest-station fallback (added after T3 exposed a second, distinct gap):** the B1-B3 interpolation above only covers SECONDARY (mid-edge) nodes; it does NOT help a PRIMARY/corner node (of a 2nd-order element, or ANY node of a linear element) that fails the tight `node_matching_BruteForce` exact match — which happens whenever the mesh spacing `elem` differs from the `.h5drm`'s native station spacing `elem_base`, because `drm_transition`'s thickness only lines up with the real box's fixed station coverage when `elem == elem_base` (confirmed root cause of a "zero response at elem=5.0m" regression across every element family, not just the higher-order ones). Fix: for any node classified as NOT secondary, a role-scoped (never distance-scoped, so it cannot reintroduce the original bug) geometric nearest-real-station lookup with a generous fallback tolerance (`kPrimaryNodeFallbackTolerance = 10.0`, hardcoded — comfortably covers the known 2.5-5m overshoot while staying far below any DRM zone thickness), gated by an O(1) DRM-box bounding-box pre-filter plus a `std::set<int>` negative-result cache (without both, the naive O(8178-station) search per unmatched node across the WHOLE domain hung for 5+ minutes with zero progress — found on a real rerun, not assumed). Companion vanilla fix in the same effort: `TenNodeTetrahedron.cpp` had a stray unconditional `std::cout` in its shape-function precompute loop that flooded stdout (~90M lines at real mesh scale) and SIGKILLed real jobs before Mumps ever ran, masquerading as OOM (see `LEDGER_quirks.md`). **Validation (real Esmeralda `OpenSeesMP` SLURM runs, LOH1 `.h5drm` `drm_s1_sta1.h5drm`, `t_total=5.0s`/1000 steps):** clean monotonic RMS-vs-mesh-size convergence at `elem=5.0m` and `elem=7.5m` for all three 2nd-order families (`BezierTet10`, `TenNodeTetrahedron`, `LadrunoBrick20` std+uri) against the `stdBrick_h2.5` baseline — 9 valid configs total, see `notebooks/adr86_all_elements_RES.ipynb` in the CERN ATLAS DRM project. `elem=2.5m` (the exact-match / zero-approximation point) is permanently NOT run for the 2nd-order families or `LadrunoBrick20` — Mumps factorization at that DOF count (1.19-2.38M DOF) repeatedly OOM'd/exceeded practical cluster budget for what is explicitly a smoke/convergence test, not a production run; `5.0m`/`7.5m` already demonstrate the mechanism converges correctly.
