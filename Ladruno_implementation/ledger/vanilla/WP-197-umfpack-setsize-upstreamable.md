| `SRC/system_of_eqn/linearSOE/umfGEN/UmfpackGenLinSOE.cpp` | `// Ladruno WP-197` (fork issue [#981](https://github.com/nmorabowen/OpenSees/issues/981)): `setSize(Graph&)` now `clear()`s `Ap`/`Ai` before rebuilding them and sizes `Ax` with `assign(nnz, 0.0)`. It used to `reserve` and `push_back` onto the old vectors, so a second `setSize` after a DOF-graph change (an `sp` after the first `analyze` under `constraints Transformation`, an element added or removed) APPENDED the new pattern: `addA` searched the old column ranges ("an element entry has no slot ... DISCARDED", a silently wrong tangent), symbolic factorization rejected a pattern whose old rows exceed the new `n` (every later solve "setSize has not been called"), and a pattern whose nnz shrank left `addA` writing past the end of `Ax`. An unchanged-graph re-analysis (no `setSize`) and the `wipeAnalysis` path are byte-identical to the base build. A FORCED re-`setSize` on an unchanged graph (`domainChange`) changes in the last bits: `umfpack_di_symbolic` reads `Ax`, and `resize` used to leave the last assembled tangent there (the first `setSize` sees zeros), so before WP-197 that run differed from the run without `domainChange`; now the two print the same bytes. **Upstream OpenSees/OpenSees master has the identical code (`setSize`, lines ~95-134): vanilla has the same bug; this row is upstreamable as is.** Workaround on an unfixed build: `wipeAnalysis` after every graph change. Test: `tests/test_wp197_umfpack_setsize.py`. | #TBD |
