| `SRC/element/Element.cpp` | `// Ladruno`: **the `index == -1` scratch-slot self-heal called the VIRTUAL `setRayleighDampingFactors`** at all **11** sites in this file (`getResistingForceIncInertia`, `getRayleighDampingForces`, the 5 `*Sensitivity` getters, `getGeometricTangentStiff`, …). Every one of them dereferences `theMatrices[index]` / `theVectors1[index]` on the very next line, so an element that **overrides** `setRayleighDampingFactors` to ignore Rayleigh damping never reaches the base allocator, `index` stays `-1`, and the result is an **access violation, not a wrong number**. Six fork elements override it exactly that way (`LadrunoUP`, `LadrunoRigidBody`, and the four penalty ties `LadrunoEmbeddedNode` / `LadrunoEmbeddedRebar` / `LadrunoKinematicCoupling` / `LadrunoDistributingCoupling`). Fix is one qualifier per site — `this->Element::setRayleighDampingFactors(...)` — so the base always allocates its own slot; the stored factors are untouched, so an element that ignores Rayleigh reports a **zero** damping force, which is what it means. **Found by the recorder-token sweep** (see [[LEDGER_implementations]]): the sweep made all fork elements chain to `Element::setResponse`, which routes `dampingForce` → `Element::getResponse(222222)` → `getRayleighDampingForces()`, and `tests/test_ladruno_response_tokens.py::test_up_tokens` crashed the interpreter on the first run. Latent before that only because nothing reached the path — but it was **never** fork-specific: **upstream's own `Subdomain` (an `Element` subclass) overrides it as a pure forwarder to `Domain::setRayleighDampingFactors`**, which likewise never sets `Element::index`, so vanilla OpenSees carries the identical crash. Only behavioural delta: the self-heal no longer re-propagates the factors into a `Subdomain`'s interior — a no-op, since it passes back the values already stored. | [#676](https://github.com/nmorabowen/OpenSees/pull/676) |
