### "Actions has been disabled for this repository" while every setting reads enabled — GitHub paused the fork for its usage (WP-180)
- **Bites:** from 2026-10-09 about 01:15 UTC, no workflow ran on any PR or push, and every merge was blocked (required checks never reported). `gh workflow run` returned `HTTP 422: Actions has been disabled for this repository`, yet `actions/permissions` read `enabled: true`, every workflow was `active`, the repo was neither archived nor disabled, and githubstatus showed no incident. Only the repo's **Actions page**, viewed while logged out, said why: *"Workflows aren't being run on this fork because of its GitHub Actions usage. A repository maintainer can re-enable them."* No API field exposes this.
- **Why:** `zone-b-nightly` and `cross-tier-nightly` run on `[self-hosted, windows, ladruno-perf]` and fire on every `schedule` and every `workflow_dispatch`. No such runner has been registered since ~2026-06-20 (#934), so each trigger left both jobs **queued for GitHub's 24-hour limit** before it cancelled them. The workflow's own comment called this "harmless". From 2026-09-09 to 10-08: 41 dispatches (703 run-hours) and 30 nightlies (495 run-hours), almost all waiting, against ~90 h of real Ubuntu work across 622 runs. Agents' frequent `workflow_dispatch` (the AGENTS.md way to get Zone-A on a draft) multiplied it.
- **Workaround/status:** the owner re-enabled Actions from the Actions page (needs a maintainer login). WP-180 makes both self-hosted jobs **opt-in** via the repository variable `WINDOWS_RUNNER=true`, which is unset by default, so they are skipped instead of parked. Set it only with a `ladruno-perf` runner actually registered. If Actions silently stops again, read the **Actions page banner** first, before suspecting settings or billing.
