### `ManzariDafalias::getState()` is SHADOWED by all four wrappers and reports a different `alpha_in` than they do — investigated for ADR-86 PR-2 and deliberately NOT "fixed"

- **The shape of it.** `getState()` returns a 26-vector `[eps_e(6) | alpha(6) | fabric(6) | alpha_in(6) | e | dGamma]`. `ManzariDafalias::getState` (`ManzariDafalias.cpp:882`) assembles **`mAlpha_in_n`** — the COMMITTED reversal reference — at offset 18. All four vanilla wrappers assemble the TRIAL **`mAlpha_in`** at the same offset, with byte-identical signatures: `ManzariDafalias3D.cpp:153`, `ManzariDafaliasPlaneStrain.cpp:176`, `ManzariDafalias3DRO.cpp:136`, `ManzariDafaliasPlaneStrainRO.cpp:176`. So do our own `LadrunoSANISAND3D.cpp:177` and `LadrunoSANISANDPlaneStrain.cpp:205` (PR-1 copied the wrapper shape). `commitState` (`:433`) does `mAlpha_in_n = mAlpha_in;`, which is what makes `_n` the committed twin.
- **`getState` is NOT virtual**, so which body runs is decided by the STATIC type at the call site. Worth knowing on its own.
- **But the wrapper bodies are unreachable in practice.** `setResponse`/`getResponse` exist only on the base (`:519`, `:546`) and are not shadowed; inside them `this` is a `ManzariDafalias*`, so `this->getState()` binds to the BASE's body **even for a `ManzariDafalias3D` object**. Every recorder therefore gets `mAlpha_in_n`. A grep of `SRC/` finds **no** caller holding a `ManzariDafalias3D*` / `ManzariDafaliasPlaneStrain*` at all, so the four wrapper `getState` bodies are dead code for every path in the tree. The base's version has defined 100 % of shipped behaviour since the class was written.
- **And nothing observable ever distinguished them anyway.** `commitState` copies `mEpsilonE`, `mAlpha`, `mFabric`, `mDGamma` and `mAlpha_in` to their committed twins and recomputes `mVoidRatio`, and `Domain::commit()` records AFTER committing — so at a recorder's actual call moment all six entries are simultaneously the committed state under either spelling. The two forms can only differ if `getState` is called mid-iteration (a script's `eleResponse` after a failed `analyze`).
- **Why ADR-86 PR-2 changed NOTHING here.** The evidence points both ways and no fact in the code settles it:
  - *For the wrappers (trial):* five of the six entries in the vector are trial, so the base's slot 18 makes the snapshot mixed-time; and six sites spell it `mAlpha_in` against the base's one.
  - *For the base (committed):* slot 18 then agrees exactly with the class's own dedicated `getAlpha_in()` accessor (`:911`, response type 6, the `alpha_in` recorder), which also returns `mAlpha_in_n`. Change `getState` and `state[18..23]` starts contradicting the `alpha_in` recorder on the same material. `mAlpha_in` is also a *reversal reference* that can flip within a step, so reporting the committed one is defensible on its own terms.
  - *The family does not settle it either:* in the same folder, `PM4Sand::getState` (`:948`) assembles `mAlpha_n`, `mFabric_n`, `mAlpha_in_n` — all COMMITTED — while `PM4Silt::getState` (`:971`) assembles `mAlpha`, `mFabric`, `mAlpha_in` — all TRIAL. Two sibling materials, same lineage, opposite answers.
  - *And it is not a copy-paste slip that drifted:* the divergence is present in **every** revision back to the 2014 introduction of `ManzariDafaliasRO` (`78d5bcc82`) and has never been touched since. It was written that way.
- **Verdict:** ADR-86 D9's error-vs-opinion test lands on **opinion**. Changing the base is the riskier edit (it is the only reachable one) and changing the wrappers picks a winner with no evidence, so PR-2 reports and leaves it. If the fork ever wants uniformity, the honest fix is to decide the whole vector at once — committed *or* trial for all six entries — not to patch offset 18.
- **What you must not do about it:** `getState` is a sibling of the `initialize()` / `GetElasticModuli` shadows at `ManzariDafaliasRO.h:93-97`. Do **not** "fix" the static-type hazard by adding `virtual`; see the dedicated entry above.
