### A fork parser that IGNORES unknown tokens "for forward-compat" silently drops a frontend's new flags -- the model runs with default physics and nothing says so (WP-167, 2026-10-05)
- **Bites:** `OPS_LadrunoRCConcrete` and `OPS_LadrunoRCFiniteStrain` ended their option ladder with `// unknown tokens are ignored (forward-compat)`. apeGmsh #1184 emitted `-crackedNu 0.2` / `-betaC 170` (declared only on open fork PR #877); this build dropped both without a word, and a misspelling (`-tensStif vc`) went the same way. "Forward-compat" here means the OLD engine pretends to understand the NEW deck.
- **Why:** an `if/else if` strcmp ladder that is the last statement of the token loop, with no final `else`, falls through on any unmatched token and the loop moves on. In `OPS_GetDoubleInput`-style parsers the silence also hides arity slips (`-Kc` at the end of the line read nothing and kept the default).
- **Status:** fixed for the LadrunoRCConcrete family (WP-167): `SRC/material/LadrunoOptSpec.h` declares every accepted option (name, value count, `since`); any other token makes the command fail with `ERROR nDMaterial <Material> <tag>: unknown option '<tok>' (build <hash>)` and the accepted list. A frontend feature-detects with `ladrunoBuild` + `since`, never by sending a flag and hoping. The quirk rule `unknown-token` (`ci/check_quirk_patterns.py`) flags the comment and the else-less ladder in fork-stamped sources; the parsers below that still let a token through are a shrink-only ratchet (`UNKNOWN_TOKEN_LEGACY`).
