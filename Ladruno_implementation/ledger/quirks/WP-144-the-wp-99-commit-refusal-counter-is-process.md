### The WP-99 commit-refusal counter is process-wide: a `commitState()` OUTSIDE `Domain::commit()` leaves it set and the NEXT `Domain::commit()` aborts (-4) with no refusal of its own (WP-144 G2)
- **Bites:** `ladrunoNoteCommitRefusal()` increments a function-local static (`LadrunoMaterialStatus.h`), and only `Domain::commit()` read-and-cleared it. Anything that calls a refusing material's `commitState()` outside a Domain commit -- an NDTest `CommitState` on a prototype or `getCopy` source, a hand-driven material, a probe -- leaves the count > 0 with nobody to consume it, so the next real `Domain::commit()` printed "N integration point(s) REFUSED this commit" and returned -1 (analysis -4) for a model with no refusal at all. Found at G2 through `test_getcopy_of_a_latched_source_is_not_latched`: the latched prototype's NDTest commit poisoned the following analysis.
  - The symptom reads like a material bug (a fresh element "refusing"); the material is innocent, the stale count is the cause. Order-dependent in a test process, invisible in a single-deck run.
- **Rule:** the counter means "refusals declared DURING the commit now being assembled". `Domain::commit()` zeroes it BEFORE the element loop (the post-loop check is unchanged), so only a refusal raised inside that loop can abort it. Nothing relies on accumulation across commits: the only reader is that check (which cleared after acting), and `PartitionedDomain::commit()` commits its own elements and then each subdomain through its own `Domain::commit()`, each checking right after its own element loop. A new caller that wants to read the count outside a commit must clear it first.
  - **NESTING (WP-144 G2 close).** The counter is shared by a parent and every in-process `Subdomain` (an Element: `Subdomain::commitState -> Subdomain::commit -> Domain::commit`), so the clear-before-the-loop must be the OUTERMOST commit's alone. The first version cleared in every `Domain::commit()`: a nested `Subdomain::commit()` inside the parent's element loop wiped the refusals the parent had collected from the elements committed before it, the parent's post-loop check read 0 and an invalid commit went through. Likewise a nested commit's own post-loop check must not CONSUME the count (`Subdomain::commit` drops the nested return, only the parent aborts).
  - **Fix:** `Domain.cpp` keeps a static nesting depth (RAII guard `LadrunoCommitDepthGuard`, restored on every early return); only depth 1 clears, before its element loop and when acting on a refusal. A nested commit with a pending count still returns -1 early and leaves the count for the parent. Serial, like the counter.
- **Workaround/status:** FIXED (WP-144 G2): `Domain::commit()` calls `ladrunoClearCommitRefusals()` before the element loop (`// Ladruno WP-144 (G2)`); regression `tests/test_ladruno_norsand.py::test_getcopy_of_a_latched_source_is_not_latched`. Needs a full rebuild to take effect in `opensees.pyd` (Domain.cpp is in `OPS_Domain`).
