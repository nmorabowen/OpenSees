### Adding `virtual` to `ManzariDafalias::initialize()` or `GetElasticModuli` would silently change every existing Ramberg-Osgood (`ManzariDafaliasRO`) deck's results
- **Bites:** anyone tempted to "clean up" the two quirks above by promoting `ManzariDafalias::initialize()` (or either `GetElasticModuli` overload) to `virtual` so a subclass can override it the normal way, instead of shadowing + re-applying. It looks like the more idiomatic C++ fix. It is a trap: doing so changes behaviour for a class that was never touched and never mentioned in the change.
- **Why:** `ManzariDafaliasRO` (`SRC/material/nD/UWmaterials/ManzariDafaliasRO.h:93-97`) already declares `void initialize();` and two `GetElasticModuli(...)` overloads with **identical signatures** to the base -- today these are non-virtual **shadows** (name hiding), so a `ManzariDafalias*` pointer to an RO object still calls the BASE version, and only code that has the concrete `ManzariDafaliasRO` type gets the RO version. The instant either base method becomes `virtual`, every one of those identical-signature shadows becomes an **override** instead, and the base integrators -- which hold `ManzariDafalias*`/`this` internally, not the derived type -- start dispatching to the Ramberg-Osgood elasticity in **every existing RO deck**, silently changing its results. A change intended to be inert for RO users would not be inert.
- **Workaround/status (2026-08-26, ADR-86 PR-1 -- avoided, not fixed, because there is nothing to fix):** `LadrunoSANISAND::initialize()` stays a **non-virtual shadow** with the identical signature, exactly like `ManzariDafaliasRO`'s -- it deliberately does NOT add `virtual` anywhere in the base. The subclass instead relies on controlling every method that IS already virtual through `NDMaterial`/`MovableObject` (`revertToStart`, `sendSelf`, `recvSelf`, both `getCopy` forms, `Print`) to "win the last write" on the two protected data members, and calls its own `initialize()`/`applyLadrunoConstants()` explicitly from each of those rather than depending on virtual dispatch into `initialize()` itself. `mElastFlag` is a separate, unrelated `static` trap already recorded elsewhere in this ledger (search "mElastFlag") -- both are reasons the Manzari family resists the naive subclassing idiom. See [[86_ladruno_sanisand_adr]] §4.1 ("the RO hazard").
