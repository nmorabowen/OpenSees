### `ManzariDafalias::mElastFlag` is STATIC — one elastic/plastic stage flag shared by every instance in the process, and any constructor resets it to elastic
- **Bites:** `mElastFlag` (`SRC/material/nD/UWmaterials/ManzariDafalias.cpp:58`) is declared `static`, not a per-instance member — every `ManzariDafalias` object in the process shares ONE stage flag. Construct a second material (a second `nDMaterial ManzariDafalias ...` command, or a `recvSelf` on a parallel worker) after you called `updateMaterialStage -material N -stage 1` on the first, and the new full constructor now defaults it to `0` again (elastic) — silently reverting EVERY existing instance's stage, not just the new one's. Two materials, "one" is elastic and "one" is plastic, is not a state this class can represent.
- **Why:** upstream wrote it this way; the parallel/classTag constructor (`:285`, used by `recvSelf`/`FEM_ObjectBroker`) already forced `mElastFlag = 0` for exactly this reason — to make sure a freshly-deserialized worker starts in the same stage-0 idiom a fresh interpreter construction would. The two Tcl/Python-facing full constructors just never got the same line (TIMs report item 7, fixed in this PR — see the `LEDGER_vanilla_files` row).
- **Rule:** never rely on `mElastFlag`'s value surviving past the NEXT `nDMaterial ManzariDafalias` command in the same process/model. If a model has more than one ManzariDafalias material and needs some elastic while others are already plastic, that is not supported by this flag — the community workaround is to explicitly call `updateMaterialStage -material N -stage S` for every tag, every time, right before the stage-dependent analysis step, rather than assuming construction order preserves anything.
- **Workaround/status:** not fixable without a wire-format-breaking change (making the flag per-instance); left as upstream's design. Recorded here so `updateMaterialStage` per material tag remains the enforced best practice rather than an optional habit. See `tests/test_manzari_safety_pack.py`, which relies on this exact behaviour for test isolation (each test constructs a fresh material, which re-defaults the shared flag to elastic regardless of what a previous test left it at).
#### Follow-up (apeGmsh #2444, 2026-10-22): the constructor reset is FIXED; the flag stays static
- **What it cost:** a staged model that flips MD to stage 1 and LATER activates more MD elements (each element's `getCopy("ThreeDimensional")` runs a full constructor) silently ran every MD material elastic from that stage on. apeGmsh measured uy -1.6597e-3 -> -1.4923e-3, the elastic answer; stock 3.8.0 never did this (its full constructors don't touch the flag, its file-scope default is 1).
- **Fix:** no constructor writes `mElastFlag` any more -- not the two full constructors (the fork's TIMs item-7 line) and not vanilla's classTag constructor (the one `getCopy()` runs as `new ManzariDafalias3D(); *clone = *this;`). The elastic default is the file-scope initialiser (now `0`) plus a reset on `wipe` (`ladrunoManzariDafaliasResetStage()` from `OPS_clearAllNDMaterial()`), so a fresh model -- and the next model after `wipe` in the same process -- still starts elastic. LadrunoSANISAND inherits the fix (it uses the base static and the base constructors); a SANISAND material activated AFTER the flip now runs its per-instance flip handling (`mFlipSeen` false -> `ladrunoRunStageFlipOnce()` -> `Elastic2Plastic`) on its first trial step, which is the designed path (a zero-stress point is primed to the isotropic `Pmin` state, no NaN). Plain MD subclasses activated after the flip simply start elastoplastic, as on stock 3.8.0.
- **The Rule above changes:** the stage now survives later `nDMaterial` / element construction within one model; it is reset only by `wipe`. It is still ONE flag for every MD instance in the process (two MD tags cannot sit in different stages), and `updateMaterialStage` still reaches only one element's material (upstream, see the ADR-92 `updatematerialstage-reaches-one-element` quirk). Test isolation in `tests/test_manzari_safety_pack.py` now comes from its `wipe`, not from construction.
- **Siblings checked:** `SAniSandMS::mElastFlag`, `PM4Sand::me2p`, `PM4Silt::me2p` are also class-wide statics, but none of their constructors writes them (only `updateParameter` and `recvSelf`) -- no change needed.
- **Gate:** `tests/test_manzari_stage_static_activation.py` (MD + LadrunoSANISAND, flip + activate == flip alone; matches stock 3.8.0 to 1e-6; next model after `wipe` is elastic) + `tests/tcl/manzari_stage_static_activation.tcl` via classic `OpenSees.exe`. Pre-fix the flip + activate leg returns exactly the elastic -2.8970896097e-3.
#### Follow-up (WP-144 K4, 2026-11-07): the PM4Sand and PM4Silt stage also survives `wipe` -- NOT fixed, noted
- **What the sibling check above missed:** it asked whether a CONSTRUCTOR writes the flag (none does). The other half of the #2444 fix, the reset on `wipe`, was never applied to the siblings. `PM4Sand::me2p` (`PM4Sand.h:206`) and `PM4Silt::me2p` (`PM4Silt.h:208`) are written only by `updateParameter` and `recvSelf`, so once any model in the process calls `updateMaterialStage ... -stage 1`, the NEXT model after `wipe` starts in the plastic stage.
- **Seen:** the K4 single-element PM4Sand driver (`Ladruno_files/testbed/norsand_calib/harness/k4_pm4sand.py`), two plane-strain cases in one interpreter: the second consolidation, from zero stress in the plastic stage, returned NaN at load factor 0.2; each case alone ran clean. Worked around by one process per case.
- **Fix if wanted (not done; owner decision 2026-11-07: note only):** the #2444 pattern, a static reset for each class called from `OPS_clearAllNDMaterial()`. It changes behaviour only for a model built after `wipe` in the same process (it then starts elastic, as in a fresh interpreter); within one model, nothing changes. Making the flag per-instance instead would change real models (elements activated after the switch would start elastic through `getCopy()`, a two-tag model that switches one tag would differ, and the wire format would change), so it is not the fix.
- `SAniSandMS::mElastFlag` was not checked for the `wipe` leak.
