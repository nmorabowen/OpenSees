# ADR-77 C0 + T0 — first measurements

> Companion results doc to [[77_ladruno_implicit_transient_adr]]. C0 is the
> consistency audit (source, no timing); T0 is the five-loop step anatomy.
> Bench: this PC, serial, `MKL_NUM_THREADS=1`, LadrunoBrick + LadrunoJ2 cube,
> Newmark(0.5,0.25) + Newton + `NormDispIncr 1e-7`, dt=2e-4.
> Harness `Ladruno_files/testbed/perf/phase77/{t0_step_anatomy.py, t0_report.py}`.

## 1. Headline — the ADR's own §3 hypothesis is NOT confirmed

ADR-77 §3 reasoned: *"with PARDISO the element loop is ~75% of a solve-bound lane
(L3-0). If the transient step behaves the same way, the target is the assembly
side."* **Gate G0 forbade assuming that transplant, and G0 earned its keep.**

Measured at n=15 (11 520 DOF, 3 375 elements, 4 steps):

| | UmfPack | PARDISO | L3-0 static lane (for contrast) |
|---|---|---|---|
| `elem.tangent` | 30.4% | **40.8%** | 35.8% → **74.9%** |
| `linearSolve` | 58.5% | **45.2%** | (minor after flip) |

**On the transient step, `linearSolve` remains the single largest loop even under
PARDISO (45.2% > 40.8%).** The element loop rises — the direction matches L3-0 —
but nowhere near the 74.9% that would have made assembly the obvious target. Wall:
6.399 s → 4.662 s, **1.37x**, answers bit-identical (`uz` relerr 0.0e+00).

**Caveat, stated up front and not resolved by this run:** these are **1-thread**
numbers, chosen so the run is a bit-exact oracle (threaded PARDISO is not
byte-reproducible, ADR-75 P1f). PARDISO's advantage grows with threads, which
would push `linearSolve` down and the element share up. L3-0's 74.9% was not
measured under the same thread count. **A thread sweep is the first T0 follow-up
(T0b) and no assembly-side conclusion should be drawn before it runs.**

Sanity check that the measurement is sound: the assembly loops are
solver-independent, as they must be — `formTangent` 1999.8 ms (Umf) vs 1985.8 ms
(PARDISO), `elem.residual` 335.50 ms in *both*. Only `linearSolve` moves. Profiler
overhead is +1.9% (Umf) / +3.3% (PARDISO) on step wall (profiled run is separate
from the timed samples, never mixed in).

## 3. G2 verdict — the constant-M/C cache is NOT authorized

**G2 headroom (element inertia re-formed every iteration + both DOF_Group loops):**

| | UmfPack | PARDISO |
|---|---:|---:|
| headroom | 211.3 ms | 210.8 ms |
| % of step | **3.24%** | **4.38%** |
| G2 gate | ≥ 10% | ≥ 10% |

**Fails the gate by better than 2x on both arms ⇒ the constant-M/C cache dies here,
at zero design cost.** This is exactly what T2 was specified to do: kill a
plausible-sounding lever before anyone designs it. ADR-77 §4.3 item 4 is closed
unless the caveat below reopens it.

**The one caveat that could reopen G2:** this deck carries its mass in the
*material* (`LadrunoJ2 -rho`), so `dof.tangent` measures almost nothing (0.27%).
A model with lumped nodal mass (`mass` commands — i.e. most building models) puts
real work in the DOF_Group loop. **Re-run G2 on a nodal-mass deck before closing
it for good.** That is now a T2 subtask, not a conclusion.

## 4. What the new instrumentation cost and bought

Two vanilla files, one coarse scope each (`// Ladruno ADR-77 T0`):

- `SRC/analysis/integrator/TransientIntegrator.cpp` — `dof.tangent`
- `SRC/analysis/integrator/IncrementalIntegrator.cpp` — `dof.residual`

Both loops were untimed; their cost was silently folded into "the rest of
`formTangent`/`formUnbalance`". The measurement confirms the P1f structural claim
that motivated ADR-77: **`IncrementalIntegrator::formTangent` (the static path)
has no DOF_Group loop at all — only the transient path assembles nodal mass.**
That asymmetry is now visible in the profile rather than only in the source.

## 5. C0 — consistency audit findings

Method note: the first pass was `grep`-based and produced **two false positives**
(Newmark reported as missing a `deltaT` guard — it has a *more* careful one:
`deltaT < 0.0 || (displ != 3 && deltaT == 0.0)`; and `StagedNewmark` reported as
having a stub `sendSelf` — it has *none*, inheriting Newmark's working one, and
declares no members of its own). **Every cell below was confirmed by reading the
function.** C0 is a read-the-source audit; grep only nominates candidates.

| # | Finding | Classes | Severity | G5 verdict |
|---|---|---|---|---|
| **C0-1** | `newStep(deltaT)` takes no validity guard and divides: `c2 = 2.0/deltaT`, `c3 = 4.0/(deltaT*deltaT)`. `analyze(n, 0.0)` yields inf/nan in the tangent instead of a clean error return. Newmark/HHT/HHTGeneralized/GeneralizedAlpha/Collocation/WilsonTheta/Newmark1 all guard. | `TRBDF2`, `TRBDF3`, `BackwardEuler`, `Houbolt` | garbage-run, no diagnostic | **patch-in-place** — adding a guard cannot change results on valid input |
| **C0-2** | `formEleTangent` has no `HALL_TANGENT` branch and **fails silently**: `BackwardEuler`/`Newmark1` `zeroTangent()` then add nothing ⇒ **a zero tangent**; `Collocation` adds `c2·C + c3·M` with **no stiffness at all**. `Newmark` at least prints `unknown FLAG`. `algorithm Newton -hall` reaches any integrator. | `BackwardEuler`, `Newmark1`, `Collocation` | **silent wrong answer** — the worst class | **patch-in-place** — add the branch, or at minimum the error return Newmark has |
| **C0-3** | `sendSelf`/`recvSelf` are stubs returning 0 without sending. Benign *today* (all three are parameterless), but latent: any future ctor argument is silently dropped in parallel/database use. **No C0 finding requires owning the class.** All four are small, greppable,
result-preserving vanilla diffs — the §4.2 pattern, and evidence *for* the ADR's
Q1b position rather than against it. They batch into one consistency-wave PR with
a `LEDGER_vanilla_files.md` row each, and are candidates for the upstream-PR
campaign.

C0-2 is the one worth prioritising: a silent zero tangent is worse than an
unsupported-option error, because the run *completes* and reports numbers.

## 6. Gotchas banked

- **The fork's parallel numberer does not exist in a serial build.** The
  registered verbs are `LadrunoParallelRCM` / `LadrunoParallelPlain` (ADR-30
  §140's `numberer LadrunoParallel` is doc shorthand and is rejected outright),
  and **both factories are wrapped in `#ifdef _PARALLEL_INTERPRETERS`** —
  `OpenSeesCommands.cpp:4774` returns 0 in serial. A null numberer makes OpenSees
  fall back to **RCM with only a warning**, so a serial bench that asks for the
  Ladruno numberer silently measures RCM. Same family as the P1d "a mistyped
  `system` costs you the SOLVER, silently" trap. **Serial T0 runs RCM by design;
  the Ladruno numberer is a T4 (parallel) knob.**
- `h5py` is **not** in the `python3.12` used to drive the bench; it is in
  `C:\Users\nmb\venv\opensees_env\Scripts\python.exe` (3.15.1). Drive the bench
  with `python3.12 -S`, read the profiles with the venv interpreter.
- The profiled run must never be one of the timed samples (it costs +2-3%).
  `t0_step_anatomy.py` runs it separately for this reason.

## 6b. T0b — the thread sweep, and the answer to §1's open question

**T0's 1-thread result WAS a 1-thread artifact. The assembly-side premise is
restored — but only under threaded PARDISO, and the crossover is at 2 threads.**

n=15, 4 steps, 2 repeats, ladder 1/2/4/8/16 (i7-13700KF, 8 P + 8 E cores). Each
thread count is a separate process: MKL reads `MKL_NUM_THREADS` at library init,
so an in-process loop would silently measure the first setting for every arm.

### PARDISO

| thr | wall_s | step_ms | `elem.tangent` | (ms) | `linearSolve` | (ms) | assembly total | verdict |
|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 1 | 4.780 | 4872 | 40.6% | 1976 | **45.6%** | 2223 | 47.8% | solve > elem |
| 2 | 3.811 | 3935 | **50.6%** | 1989 | 32.2% | 1267 | 59.6% | **elem > solve** |
| 4 | **3.519** | 3652 | **54.9%** | 2006 | 26.3% | 960 | **64.7%** | elem > solve |
| 8 | 3.563 | 3720 | 59.2% | 2202 | 20.7% | 771 | 69.9% | elem > solve |
| 16 | 3.921 | 4058 | 62.7% | 2543 | 16.5% | 671 | **73.9%** | elem > solve |

### UmfPack (control — serial factorization)

| thr | wall_s | `elem.tangent` | `linearSolve` | verdict |
|---:|---:|---:|---:|---|
| 1 | 6.459 | 30.1% | 58.8% | solve > elem |
| 4 | 5.609 | 35.0% | 52.1% | solve > elem |
| 16 | 6.383 | 38.2% | 48.3% | solve > elem |

**UmfPack never crosses over at any thread count.** So the flip is a property of
*PARDISO*, not of the transient path — the right statement is "a fast threaded
solver makes assembly dominant", not "transient steps are assembly-bound". At 16
threads PARDISO's assembly total reaches **73.9%**, essentially L3-0's 74.9%.

### The measurement is trustworthy in the ≤4 rows only

`elem.tangent` **absolute ms** is the control variable, and it is flat to 4
threads (**1.5%** spread PARDISO, **0.3%** UmfPack — the element kernels work on
24x24 matrices, so MKL runs them serially, as expected). It then **rises** at
8/16 threads (1976 → 2543 ms), **identically in both arms**, which rules out any
solver-specific cause: those are MKL worker threads (spin-wait by default)
contending with the serial element loop on a hybrid P/E part. Consequence:

- the ≤4-thread rows are clean and carry the conclusion;
- the 8/16 rows must **not** be read as "assembly got worse" — the share is real
  but the ms is contaminated;
- **more threads is worse past 4 on this deck**: PARDISO wall bottoms at 3.519 s
  (4 thr) and degrades to 3.921 s (16 thr). ADR-75's 4-thread default is
  vindicated on the transient path too.

### Two side-confirmations

- **Threaded PARDISO non-reproducibility (P1f) reproduced independently.**
  `uz` relerr is exactly 0.0e+00 at 1 and 2 threads, and 1.1e-16 at 4/8/16. The
  ADR-75b policy (1 thread for oracle runs) is correct and now has a second
  witness on a different deck and analysis type.
- **G2 stays dead at every thread count.** Headroom rises only because the step
  shrinks: 4.43% (1 thr) → 5.87% (4) → 6.85% (16), never approaching the 10%
  gate. The constant-M/C cache is closed on this deck regardless of threading;
  only the nodal-mass re-run (§3) could reopen it.

### What T0b means for the cross-ADR picture

`elem.tangent` alone is **50-63% of the step at 2-16 threads** on the implicit
transient path under PARDISO. ADR-75b's L3-0b de-authorized threaded assembly
(L3-1) after `-commitSolveState` dropped its loop-A share to 38.95% on an
**explicit** deck. Those are different loops in different taxonomies and this
result does **not** by itself re-authorize L3-1 — but it does say the *implicit
transient* path is a materially better threading candidate than the explicit path
that de-authorized it, and ADR-75b should re-ask the question with its own loop
taxonomy on this lane. Recorded as a hand-off, not a decision.

## 6c. T1 — the reuse levers, and why the obvious inference from T0b is wrong

**The tempting conclusion from T0b — "assembly is 65% of the step, so the levers
that skip assembly must win" — is FALSE, and T1 measured it rather than
inheriting it.** On this deck, at the 4-thread operating point, *every* reuse
lever loses to plain `Newton` at low nonlinearity, and the ranking then changes
twice as nonlinearity rises.

n=15, 4 steps, PARDISO, 4 threads, `NormDispIncr` 1e-7 — **identical tolerance on
every arm**, which is what makes the comparison fair. `~` = derived by
difference (see the instrumentation gap, C0-5).

### load ×1 — peak von Mises 252 MPa (1% past yield)

| algorithm | wall_s | vs Newton | it/step | ms/iter | asm% | solve% |
|---|---:|---:|---:|---:|---:|---:|
| **Newton** | **3.498** | **1.00x** | 4.25 | 205.7 | 65.3 | 25.6 |
| Newton -initial | 8.506 | 0.41x | 16.50 | 128.9 | 36.4 | 52.4 |
| ModifiedNewton | 4.444 | 0.79x | 16.50 | 67.3 | 51.5 | 24.6 |
| ModifiedNewton -initial | 4.185 | 0.84x | 16.50 | 63.4 | 46.2 | 26.5 |
| ModifiedNewton -initial -factoronce | 4.118 | 0.85x | 16.50 | 62.4 | 46.3 | 24.2 |
| KrylovNewton | 3.651 | 0.96x | 12.50 | 73.0 | 58.8 | 27.4~ |

**Why the levers lose, in one line:** `ModifiedNewton` cuts cost-per-iteration to
**0.33x** but raises iteration count to **3.88x** ⇒ net **1.27x slower**. The
lever works exactly as advertised and still loses, because the iteration-count
penalty is the bigger term. `Newton -initial` is the worst arm at **0.41x** —
it pays full re-factorization every iteration *and* takes initial-stiffness
iteration counts, which is precisely the "expensive spelling" ADR-76 R1 warns
about, here measured on the transient path.

### load ×4 (612 MPa, 2.4× yield) and ×10 (1773 MPa, 7× yield)

| algorithm | ×4 | ×10 |
|---|---|---|
| Newton | **8.186 s** (7.25 it/step) | **DIVERGES** — fails at 2500 iterations |
| ModifiedNewton family | converges in **514** iterations | converges in **751** iterations |
| **KrylovNewton** | **4.675 s — 1.75x faster than Newton** (34.75 it/step) | **5.731 s** (44.25 it/step) — the only practical arm |

### Three corrections T1 forced on its own first reading

1. **"DID NOT CONVERGE" was a `maxIter` artifact, not a mathematical failure.**
   The first sweep ran `maxIter=300` and reported the whole initial-stiffness
   family as failing at ×4 and ×10. Re-running with `maxIter=3000`/`6000` shows
   they converge fine — **514** iterations at ×4, **751** at ×10, to the same
   answer (relerr ≤ 2.9e-16). The harness now prints `hit maxIter`, not
   "did not converge". Slow ≠ stalled ≠ divergent, and the run log cannot tell
   you which without the probe.
2. **The robustness ordering INVERTS at high nonlinearity, opposite to the
   read the ×4 row alone suggests.** At ×10 `Newton` genuinely fails (verified
   to 2500 iterations; residual growing, `deltaR` 2.7e8) while `ModifiedNewton`
   converges in 751. So the modified/initial-stiffness family is **not fragile —
   it is the robustness fallback**, earning its keep exactly where full Newton
   breaks. That is ADR-76 R1's user rule, now with transient evidence behind it.
3. **`KrylovNewton`'s split was reported as 0.0%/0.0%, which was a fabrication
   of the reporter, not a measurement.** Cause is C0-5 below; the reporter now
   derives it by difference and flags it `~`.

### C0-5 (new, found by T1) — the profiler instruments 3 of 11 solution algorithms

`Linear`, `ModifiedNewton`, `NewtonRaphson` carry the P3 scopes
(`formTangent`/`formUnbalance`/`linearSolve`/`update`/`convTest`). **Eight do
not** — `KrylovNewton`, `BFGS`, `Broyden`, `NewtonLineSearch`,
`AcceleratedNewton`, `ExpressNewton`, `NewtonHallM`, `PeriodicNewton` — so their
steps have no wrapper scopes and the solve time falls into the unattributed
remainder of `solveCurrentStep`. The leaf scopes still appear (they live in the
integrator, not the algorithm), so assembly is still measured and solve can be
derived by difference — but **the best-performing algorithm in this entire study
is the one the profiler cannot decompose**. Classification: **patch-in-place**
(add the same six scopes to the other eight), one ledger row, no ownership —
another instance of the §4.2 rule, found empirically rather than by audit.

### ADR-76 §3's trap does NOT fire on fork-authored materials

Checked in source before trusting the `-initial` arms:
`LadrunoJ2::getInitialTangent()` builds the elastic tangent (state-independent)
and `LadrunoBrick::getInitialStiff()` computes `Ki` **once and caches it**. So on
this deck `-initial` is a genuine initial-stiffness iteration with a nearly free
assembly — and `-factoronce` is *mathematically* legitimate (constant `Ki`,
constant Rayleigh, constant `dt` ⇒ genuinely constant `K_eff`), confirmed by the
answer check (relerr 3.3e-11) rather than assumed. **ADR-76 §3's warning is an
upstream-material property, not a fork-wide one** — worth stating because the ADR
currently reads as if it applies everywhere.

### The deck caveat, stated plainly

The ×1 deck is only 1% past yield (252.5 vs s0 = 250), which is why
`ModifiedNewton` and `ModifiedNewton -initial` return *identical* iteration
counts there — K_t ≈ K_i. That is also why the load sweep exists: a single-load
T1 would have published a near-elastic result as a nonlinear one. The ×10 arm is
an impulsive step load driving 7× yield in one 2e-4 s step; its physical realism
is **not** claimed — it is a robustness stress test, and only the *relative*
ordering should be read from it.

## 6d. T3 — scheme shootout: **G3 NOT AUTHORIZED**, and a confirmed bug in `GeneralizedAlpha`

Two deliverables, one of them unplanned.

### 6d.1 The G3 verdict — implicit Bathe β1/β2 is CLOSED

n=10, ramp load to 12.5% yielded GPs, PARDISO, 4 threads, `KrylovNewton` held
fixed, cost interpolated in log-log to a **common error target** (comparing at
equal dt would reward a damped scheme twice — cheaper *and* less accurate).
Reference self-convergence 3.23e-05, so both targets are well clear of the floor.

| scheme | ρ∞ | obs. order | cost @ err 5e-3 | @ 1e-2 |
|---|---:|---:|---:|---:|
| **Newmark(0.5,0.25) trapezoidal** | 1.000 | 1.67 | **2709 (1.00x)** | 1852 (1.01x) |
| **HHT(0.80)** | 0.667 | 2.16 | 2929 (1.08x) | **1833 (1.00x)** |
| HHT(0.90) | 0.818 | 2.17 | 2897 (1.07x) | 1902 (1.04x) |
| TRBDF2 | — | 2.09 | 3392 (1.25x) | 2160 (1.18x) |
| Newmark(0.6,0.3025) damped | — | 1.04 | 4339 (1.60x) | 2293 (1.25x) |
| BackwardEuler | 0.000 | 1.59 | 4271 (1.58x) | 2819 (1.54x) |

**G3 requires TRBDF2 *and* the best damped scheme each to lose ≥1.3×. TRBDF2
loses 1.18-1.25× and the best damped scheme loses 1.00-1.07×. ⇒ G3 NOT
AUTHORIZED at either target.** The modern implicit Bathe β1/β2 lane
(ADR-49a Rank 3) is **closed with the benchmark on record** — which was
precisely ADR-49a's "assess before committing" deliverable.

**The T3 hypothesis in ADR-77 §5 is also falsified.** It expected ρ∞ damping to
buy fewer Newton iterations on a stiff/nonlinear deck. Iterations/step are
**identical to three digits across Newmark, HHT(0.9), HHT(0.8), TRBDF2 and
BackwardEuler** (82.20 / 41.98 / 21.80 / 11.80 down the dt ladder). Numerical
damping bought **exactly zero** iteration reduction here. Damping is an accuracy
and high-frequency-content lever on this deck, not a convergence lever.

Order sanity, which is how the harness earns trust: HHT reads 2.16-2.17 (2nd
order ✔), TRBDF2 2.09 (✔), `Newmark(0.6,0.3025)` **1.04** — correct, γ≠½ makes
Newmark first-order — and BackwardEuler 1.59 for a 1st-order scheme.

### 6d.2 C0-6 — `GeneralizedAlpha::update()` discards the αM-weighted acceleration

`SRC/analysis/integrator/GeneralizedAlpha.cpp:405` computes `Ualphadotdot` and
then does not use it:

```cpp
Ualphadotdot->addVector((1.0-alphaM), *Udotdot, alphaM);   // computed...
theModel->setResponse(*Ualpha, *Ualphadot, *Udotdot);      // ...and discarded
```

The separate αM weighting of the **acceleration** is the one thing that
distinguishes generalized-α from HHT. `newStep()` sets it correctly
(`setAccel(*Ualphadotdot)`, line 193) and `update()` then overwrites it with the
unweighted `Udotdot` on every Newton iteration, so the inertia term is evaluated
at the wrong time point. (The identical line in `HHT.cpp:394` is **correct** —
HHT weights only stiffness/damping and its inertia genuinely sits at t+Δt.)

**Diagnosis confirmed by prediction, not by inspection alone.** If the cause is
the discarded weighting, the bug must vanish exactly at `alphaM = 1.0`, where
`Ualphadotdot ≡ Udotdot`. Measured at n=5, dt=2e-5, vs a fine reference:

| αM (αF) | ρ∞ | L2 error | it/step |
|---:|---:|---:|---:|
| HHT(0.8) — control | 0.667 | 2.07e-2 | 48.73 |
| **1.00** (0.667) | 0.5 | **2.16e-2** ✅ | 48.40 |
| 0.80 (0.60) | 0.667 | 1.01e-1 | 129.85 |
| 0.65 (0.55) | 0.818 | 7.68e-1 | 168.62 |
| 0.50 (0.50) | 1.0 | **2.01e+2** | 229.18 |

Error grows monotonically with distance from αM=1.0 and the arm is sane exactly
at αM=1.0 — the predicted signature. The T3 sweep independently reports
**negative observed convergence order** (−6.98, −2.81) for these arms: error
*grows* as Δt shrinks, which no consistent scheme does.

**Blast radius includes the fork.** `LadrunoGeneralizedAlpha` (ADR-52 W3-I2, the
DDM/sensitivity generalized-α) is `: public GeneralizedAlpha` and **does not
override `update()`**, so it inherits the defect. Measured byte-identically:
both give L2 7.6821e-01 at αM=0.65 and both give 2.1643e-02 at αM=1.0. **A fork
feature shipped on top of a broken base.**

**Classification under the §4.2 ownership rule: PATCH-IN-PLACE**, one
`LEDGER_vanilla_files.md` row, upstream-PR candidate. It is the precedent
table's first row exactly — an outright bug where vanilla behaviour is
indefensible and the fix *preserves* results on already-correct input (αM=1.0
is unchanged by construction). Note this is the single most consequential defect
the whole study found, and it still does **not** justify owning the class — a
sharper Q1b data point than anything in the C0 source audit.

### 6d.3 C0-6 FIXED, rebuilt, and verified — and G3 recomputed on valid data

**Applied to the VANILLA base class, not the fork class.** `LadrunoGeneralizedAlpha`
inherits `update()` rather than overriding it, so one line in
`GeneralizedAlpha::update()` fixes both. Overriding in the fork class would have
duplicated ~40 lines *and* left vanilla `GeneralizedAlpha` broken for every other
user — the §4.2 rule pointing at patch-in-place, and a concrete illustration of
why "own it to fix it" is the wrong instinct.

Rebuilt (`build.bat OpenSeesPy`, `dist/bin/opensees.pyd`) and verified by
`c06_genalpha_verify.py` (`before` baseline captured pre-rebuild, `after`
compared bit-for-bit). **All 8 checks pass:**

| αM | observed order before | after | it/step before → after |
|---:|---:|---:|---|
| **1.00 (regression guard)** | +1.41 | **+1.41, BIT-IDENTICAL** | 48.40 → 48.40 |
| 0.80 | −1.34 | **+1.30** | 129.85 → 48.40 |
| 0.65 | −4.41 | **+1.18** | 168.62 → 48.62 |
| 0.50 | −6.71 | **+1.19** | 229.18 → 48.40 |

`LadrunoGeneralizedAlpha` tracks the base bit-identically before and after, as it
must. A physical check that was *not* built into the test and now holds anyway:
post-fix, error decreases monotonically as ρ∞ rises (2.16e-2 → 1.82e-2 → 1.63e-2
→ **1.58e-2** at ρ∞=1) — less numerical damping is more accurate on a resolved
response. Pre-fix that ordering was meaningless.

deterministic run-to-run (identical observed orders across both T3 runs), but
wall-clock is not: Newmark trapezoidal's cost@5e-3 moved 2709 → 2385 (−12%)
between two runs of *identical* code. **Cost ratios below ~1.2× are inside that
noise** and should not be read as a ranking. G3's 1.3× bar sits above the floor,
so the verdict is safe; the "Newmark vs GeneralizedAlpha vs HHT" ordering at the
top of the table is *not* resolved by this data, and the honest statement is that
those three are indistinguishable here.

### C0-3 is withdrawn — my own audit over-called it

`TRBDF2`/`TRBDF3`/`Houbolt` are all constructed **parameterless**
(`new TRBDF2()` etc.), so `return 0` without sending is the **correct**
implementation, not a stub. There is genuinely nothing to serialize. The finding
was filed by pattern-matching the shape against the contact handler's P1a stubs;
reading the constructors kills it. TRBDF3 and Houbolt already said
`// nothing to send` — only TRBDF2 lacked the note, which is the whole reason it
looked different. A comment was added to TRBDF2 so the next reader does not
repeat the mistake. **This is the third false positive the C0 audit has produced
(after the Newmark `deltaT` guard and the `StagedNewmark` sendSelf), and all
three came from grep-shaped reasoning that reading the function dissolved.**

### C0-2 was the one worth prioritising, and the fix is confirmed

Pre-fix, `algorithm Newton -hall` on these three assembled a tangent with no
stiffness — all-zero for `BackwardEuler`/`Newmark1`, and `c2·C + c3·M` for
`Collocation` (worse, because it *looks* populated). `HALL_TANGENT` is reachable
from `NewtonRaphson -hall`, `ModifiedNewton -hall`, `NewtonHallM` and
`ExpressNewton`. Post-fix, measured:

| arm | uz | vs plain Newmark |
|---|---|---|
| `BackwardEuler -hall` | −1.932969365069346e-02 | 3.7e-02 (= its own non-hall answer exactly) |
| `Newmark1 -hall` | −2.0078594054128318e-02 | **3.5e-16** |
| `Collocation -hall` | −2.0078594054137835e-02 | **4.7e-13** |

`BackwardEuler -hall` reproducing its own non-`-hall` answer *exactly* is the
expected result, not a coincidence: with `Kt ≈ Ki` on this deck,
`cFactor·Kt + iFactor·Ki → K` because the Hall factors sum to 1 (0.2 + 0.8).

### C0-5 verified on the file that motivated it

`KrylovNewton`'s unattributed remainder fell from **~28.6% to 0.2%**;
`formTangent` 27.2% / `formUnbalance` 22.6% / `linearSolve` 19.0% / `update`
12.5% are now resolved. **Known cosmetic limitation:** because that file has two
same-named `formTangent` scopes, the integrator's deep `elem.tangent` /
`dof.tangent` leaves surface as *siblings* of `formTangent` in the rollup rather
than nested under it (they nest correctly in `NewtonRaphson`). Accounting is
complete either way — only the tree shape is affected. Recorded, not fixed.

### The no-regression claim, and the noise floor that nearly hid it

Every patch in the wave claims "cannot change results on valid input". Tested
against an oracle that predates the wave: the **committed `t3_scheme_shootout.json`**,
whose 32 (scheme, dt) `rel_err` points were produced by the previous build and
cover all four C0-1 classes plus 8 integrators.

First result: **31 of 32 bit-identical, one point drifted 1.22e-12**
(`HHT(0.80)`, dt=1e-05) — which my harness flagged as a regression at its 1e-12
gate. **The gate was wrong, not the code.** T3 runs at 4 threads and threaded
PARDISO is not bit-reproducible (ADR-75 P1f; T0b measured 1.1e-16 per step,
which compounds through ~80 Newton iterations and an L2 norm).

**Control run — the same build compared against itself:** drift of **9.82e-13 on
the very same point**. Identical code, identical magnitude. So ~1e-12 is the
solver's own floor at 4 threads and the wave is result-preserving. The gate is
now 1e-11 with that measurement written next to it. **A regression harness whose
threshold sits below its oracle's reproducibility floor reports noise as
failure** — worth remembering the next time a "1 point changed" result appears.

## 6f. T2 — the nodal-mass caveat, settled by being **falsified**

T0 killed G2 at 3.2-4.4% headroom but left one caveat open: that deck carries
mass in the *material* (`-rho`), so the DOF_Group loop measured 0.27%, and
"a model with lumped nodal mass — i.e. most building models — puts real work in
that loop." T2 holds geometry, material, load, solver and step count fixed and
moves **only where the mass lives**.

n=15, PARDISO, 4 threads (the T0b operating point, where the headroom *share* is
largest because the step is shortest).

| arm | step_ms | dof.tan | dof.res | inertia | **headroom** | gate ≥10% |
|---|---:|---:|---:|---:|---:|---|
| A material mass (= T0 deck) | 4004.8 | 0.36% | 0.12% | 5.35% | **5.83%** | fail |
| B nodal mass | 3770.6 | 0.37% | 0.18% | 5.35% | **5.90%** | fail |
| C nodal + Rayleigh `betaK0` (C constant) | 4583.5 | 0.35% | 0.16% | 10.40% | **10.91%** | **PASS** |
| D nodal + Rayleigh `betaKcurr` (C varies) | 7912.4 | 0.20% | 0.10% | 5.79% | **6.09%** | fail |

### 1. The caveat is false — nodal mass does *not* load the DOF_Group loop

A → B moves **all** inertia from the material to `mass` commands, and
`dof.tangent` goes **0.36% → 0.37%**. Nothing. The predicted mechanism simply
does not exist: the DOF_Group loop assembles 3x3 lumped nodal matrices, which is
trivial next to element assembly no matter how much of the mass it carries.
**The caveat that kept G2 open is settled by disproof, not by confirmation** —
and it would have stayed a plausible-sounding open item indefinitely if it had
not been measured.

### 2. G2's gate *is* cleared — by a mechanism nobody predicted

Not the DOF_Group loop: **Rayleigh damping**. `Element::getDamp()` (checked in
source, `SRC/element/Element.cpp`) does
`theMatrix->addMatrix(0.0, this->getMass(), alphaM)` whenever `alphaM != 0`, so
with any mass-proportional damping the **element mass matrix is formed twice per
element per iteration** — once for the M term, once inside C. Absolute
mass-formation work per 4 steps:

| arm | mass formation | |
|---|---:|---|
| A / B (no Rayleigh) | 214 / 202 ms | formed once |
| C / D (Rayleigh, `alphaM`=0.5) | **477 / 458 ms** | **formed twice** |

### 3. The pass is configuration-dependent, and D shows why the share misleads

C and D do **the same ~460-477 ms of cacheable mass work**. C clears the gate at
10.91% and D fails at 6.09% purely because D's *step* is 1.9x longer —
`betaKcurr` forces a full `getTangentStiff()` inside `getDamp()` on top of the
one already formed for K. The cacheable work did not shrink; the denominator
grew. **A percentage-of-step gate rewards a deck for having less other work**,
which is worth remembering before treating 10.91% vs 6.09% as a difference in
the lever's value.

**Practical finding for users, independent of G2:** `rayleigh` with
`betaKcurr` costs **1.86x** the step of `betaKinit` on this deck (7.751 s vs
4.176 s) for a nearly identical answer (uz differs 5.7e-5 relative). If
initial-stiffness damping is acceptable for the model, it is much cheaper.

### 4. G2 verdict — authorized, but the ADR's envisioned design is the wrong one

**G2 passes** on a fork-real configuration (nodal mass + `alphaM` Rayleigh is
ordinary building-model practice), so the lever is authorized. But every
milligram of the measured headroom is **element-local mass re-formation**, not
integrator-level M/C assembly — so §4.3 item 4's "constant-M/C tangent-contribution
cache at the `FE_Element`/integrator-interface layer" is **not** what this
evidence supports.

What it supports is much smaller: **cache the element mass matrix inside the
element**, exactly mirroring the `Ki` cache `LadrunoBrick` already keeps.
Today `LadrunoBrick::getMass()` calls `formInertiaTerms(1)` unconditionally and
returns a **class-level `static Matrix mass`** (`LadrunoBrick.h:231`) — note that
this is also the shared-static idiom [[75b_ladruno_threaded_assembly_adr]] §5.4
lists as a threading blocker, so a per-instance `Mi` cache would retire one
hazard while removing the recompute.

**Constraint carried over from ADR-76 App. A.4, not to be skipped:** mass
invariance must be an **opt-in element property defaulting to false**.
`formInertiaTerms` runs `computeBasis()` on current coordinates, so under
`-geom` finite kinematics the assumption needs its own proof before the cache
may fire. The cheap, safe first cut is to cache only when the element is in a
small-strain configuration, and to leave every other path recomputing.

Estimated ceiling if implemented: **~10.4% of step** on arm C, ~5.4% without
Rayleigh — real, but an element-owned ~10-line change, not an architecture.

## 6g. G2 implemented — the LadrunoBrick per-instance mass cache, shipped and verified

§6f's redirected design is now code: `LadrunoBrick::getMass()` caches M in a
per-instance `Mi` (the `Ki` idiom applied to mass), with invariance **checked on
every call** rather than assumed — the guard compares the only two mutable
inputs (per-GP rho, which IS mutable via the material's `setParameter "rho"`,
and nodal coordinates via `getCrds()`): 32 double compares (~ns) against a
~1.5 µs re-formation. A guard trip re-forms and re-fills. Escape:
`element ... -noMassCache`. Cost: ~4.6 KB + 256 B per element.

**One claim in §6f is corrected by the source:** it said `formInertiaTerms`
runs `computeBasis()` on *current* coordinates, requiring a `-geom` proof.
False — `computeBasis()` uses `getCrds()` (initial coordinates) in **every**
formulation; the comment at the finite kernel says the mass is
reference-configuration *by design*. So the cache is valid across all
formulations, and the `-geom corot` A/B check below is the empirical witness.

Deliberately NOT cached: the residual (`tangFlag==0`) inertia pass — (i) for
`massType==1` the residual is consistent-mass-based while M is lumped, so
`resid = M·a` would change answers; (ii) even for consistent mass, `M·a`
reorders the FP accumulation and breaks G-BYTE. That pass stays on the ADR-68
T7 skip.

### Acceptance — 11 checks, all pass (`g2_mass_cache_verify.py`)

- **1-thread on/off, 4 arm configs: EXACTLY equal** (the authoritative check,
  where PARDISO is bit-reproducible).
- **4-thread vs the pre-cache baseline: drift ≤ 2.3e-16 — and the CONTROL
  attributes it.** The `-noMassCache` arm (the unmodified old code path) shows
  the *same* drift as the cached arm; on the first sample the old path missed
  the baseline while the new path hit it exactly. That is P1f's threaded-PARDISO
  distribution resampling itself, not a cache effect. (My first gate was 1e-16
  — *below the observed ulp* — and flagged all four arms: the C0-wave
  threshold lesson, relearned at 4 threads.)
- **`-geom corot` A/B: exact** (`-geom finite` refuses LadrunoJ2 by design —
  it requires a `setTrialF` material — so corot is the geometric-nonlinear
  witness).
- **rho-guard liveness:** density tripled mid-analysis via
  `parameter/updateParameter` on all 216 elements; cached and uncached answers
  stay byte-equal. Without the guard this is exactly the ADR-76 staleness trap.

### Measured win (same T2 deck, profiled steps, n=15, PARDISO 4T)

| arm | tangent-side inertia | step |
|---|---:|---:|
| A material mass | 128 → **6.8 ms** (one formation, then cached) | 4004.8 → 3718.8 ms (**−7.1%**) |
| B nodal mass | → 7.0 ms | 3770.6 → 3586.9 ms (−4.9%) |
| C nodal + Rayleigh βK0 | 383 → **0.00 ms** | 4583.5 → 4007.2 ms (**−12.6%**) |
| D nodal + Rayleigh βKcurr | → 0.00 ms | 7912.4 → 7639.1 ms (−3.5%) |

The residual-side inertia (~82–94 ms, 1.2–2.3%) remains by design. Wall-clock
deltas carry the usual ±noise; the *attributed* deletion (383→0) is exact.

**Scope note:** `LadrunoBrick` (33002) only. `LadrunoBrick20` already has its
own rho-signature mass cache (F-1, [#583](https://github.com/nmorabowen/OpenSees/pull/583));
upstream bricks are untouched (vanilla footprint zero for this change — it is
entirely fork-owned code, so no vanilla-ledger row either).

## 7. What this changes in ADR-77

1. **§3's assembly-side premise is RESTORED, with a precise condition attached**
   (T0b): it holds under threaded PARDISO from **2 threads up** (assembly 59.6%
   at 2 thr, 64.7% at 4 thr) and fails at 1 thread (47.8%) and under UmfPack at
   every thread count. The correct claim is *"a fast threaded solver makes
   assembly dominant"*, not *"transient steps are assembly-bound"*. G0 was right
   to demand the measurement: the answer is **thread-** and **solver-dependent**,
   which neither the L3-0 transplant nor T0 alone would have revealed.
2. ~~**G2 fails its gate at every thread count**~~ ✅ **T2 SETTLED IT (§6f), and
   flipped it.** The nodal-mass caveat is **false** (moving all mass to nodes
   moved `dof.tangent` 0.36% → 0.37%), but G2 **passes at 10.91%** via an
   unpredicted route: `Element::getDamp()` calls `getMass()` when `alphaM != 0`,
   so Rayleigh doubles element mass formation. **G2 AUTHORIZED — but the
   evidence supports caching the mass matrix *in the element* (mirroring
   `LadrunoBrick`'s existing `Ki` cache), NOT the integrator-level constant-M/C
   cache §4.3 item 4 envisioned.**
3. **C0 delivers 4 confirmed patch-in-place findings, 0 requiring ownership** —
   consistent with the ADR's Q1b position, now with evidence.
4. Bench-stack correction: serial T0 is **RCM**, not the Ladruno numberer; and
   **`MKL_NUM_THREADS=4` is the operating point** for this deck (wall degrades
   past 4 on a hybrid P/E part).
5. ~~**T1 is now the live stage**~~ ✅ **T1 MEASURED (§6c)** — and it **falsified
   the inference T0b invited**. Assembly being ~65% of the step did *not* make
   the assembly-skipping levers win: at low nonlinearity every lever loses to
   plain `Newton` (0.41-0.96x), because `ModifiedNewton` buys a 0.33x cheaper
   iteration at the price of 3.88x more of them. The winner is
   nonlinearity-dependent: **Newton at ×1, KrylovNewton at ×4 (1.75x) and ×10
   (the only practical arm)**. `KrylovNewton` is never worse than ~0.96x and is
   the standout of the study.
6. **The modified/initial-stiffness family is a ROBUSTNESS lever, not a speed
   lever** — at ×10 `Newton` diverges (verified to 2500 iterations) while
   `ModifiedNewton` converges in 751. This **re-motivates `LadrunoModifiedNewton`
   (ADR-76 §4.5) on robustness grounds while removing its speed justification**;
   §7's open item 2 should be decided on that basis.
7. ✅ **C0 PATCH WAVE COMPLETE (§6e).** C0-1/C0-2/C0-4/C0-5 fixed, rebuilt and
   verified; **C0-3 WITHDRAWN as a false positive** (parameterless classes —
   `return 0` was always correct). **15 vanilla files, 15 ledger rows, zero fork
   classes.** No-regression proven against the committed T3 oracle, after a
   control run showed the harness's own 1e-12 gate sat *below* threaded
   PARDISO's ~1e-12 reproducibility floor.
8. **ADR-76 §3's `getInitialTangent()` trap does not fire on fork materials**
   (`LadrunoJ2` overrides it; `LadrunoBrick` caches `Ki`) — the ADR reads as if
   the warning is universal and should be scoped to upstream materials.
9. ✅ **T3 MEASURED (§6d): G3 is NOT AUTHORIZED.** TRBDF2 loses only 1.18-1.25x
   and the best damped scheme 1.00-1.07x against a ≥1.3x bar ⇒ **the implicit
   Bathe β1/β2 lane (ADR-49a Rank 3) is CLOSED with the benchmark on record.**
   §5's T3 hypothesis is falsified too: numerical damping bought **zero**
   iteration reduction (identical it/step across all schemes).
10. 🔴 **C0-6 — a confirmed BUG in `GeneralizedAlpha::update()`**: the
   αM-weighted acceleration is computed and then discarded, so the inertia term
   sits at the wrong time point on every Newton iteration. **`LadrunoGeneralizedAlpha`
   inherits it** (no `update()` override) — ADR-52 W3-I2 shipped on a broken
   base. Both are trustworthy **only at αM=1.0 (ρ∞=0.5)**. One-line
   patch-in-place; ✅ **APPLIED to the vanilla base (not the fork class), rebuilt

   −1.34/−4.41/−6.71 → +1.30/+1.18/+1.19.** G3 was then **recomputed on valid
   data and still says NOT AUTHORIZED** — the repaired GeneralizedAlpha is now the
   *second-best* scheme (1.05x), which leaves even less room for Bathe. ADR-49a
   calls GeneralizedAlpha the "gold standard"; that row needs a caveat for every
